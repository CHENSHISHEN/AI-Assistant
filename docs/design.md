# 私人助手（OpenClaw）设计文档

- 日期：2026-11-20
- 状态：用户已批准（2026-11-20）；P0–P3 已实施（2026-11-22），实施中落定的决定见第 11 节
- 部署位置：单台 Linux 服务器（自托管）

## 1. 要做什么、为什么

用户在这台服务器上同时跑着很多 agent 会话（Claude Code、Codex 等，由 Orca 管理），还有一批自建应用（由 Workbench 登记和启停）。靠人盯不过来。

要做的是一个只服务用户本人的私人助手：用户在 Telegram 里和它对话，它也会主动推送提醒。管会话、盯任务、管应用只是起步的例子，以后新能力靠加 skill 扩展。

## 2. 目标、非目标、反目标

**目标**
- 在 Telegram 私聊里查询并操作 agent 会话：列表、搜索、读进度、回复确认、启动 agent。
- 主动提醒：应用挂了、会话卡住等待确认、任务做完了。
- 应用管理：查状态和日志；启停、重启要由用户确认后执行。
- 能力可扩展：新增场景只加 skill 和网关接口，不改架构。
- 预留飞书作为第二个入口。

**非目标**
- 不重写 Orca 和 Workbench 的功能，只调用它们。
- 第一期不接飞书。
- 不做多用户。
- 不把控制台暴露到公网。
- 不自动修复应用：只通知，用户确认后才处理。

**反目标**（功能都正常，但出现下面任何一条也算失败）
- 凭据（密码、token、私钥等）经由 Telegram、模型或日志流出。
- 陌生人能和助手对话，或者能调用网关。
- 危险操作绕过拦截被执行，包括模型自己批准自己。
- 提醒太多变成噪音，用户开始忽略。
- 配置在容器里被改动，和仓库不一致，导致无法重建。

| 编号 | 决策 | 来源 |
|---|---|---|
| D1 | 使用 OpenClaw，Docker 部署在本机 | 用户 |
| D2 | 会话和任务能力复用 Orca，应用能力复用 Workbench，不重复造轮子 | 用户 |
| D3 | 入口有两个：先做 Telegram，飞书预留 | 用户 |

| D6 | 只给用户本人使用。防护的重点是三件事：输出关卡（凭据不外发）、认证（只认用户本人）、漏洞防护（不暴露、不被诱导执行危险操作）。不对任何资料目录做屏蔽 | 用户 |

## 4. 方案比较

| 方案 | 做法 | 优点 | 代价 | 结论 |
|---|---|---|---|---|
| A. Docker 容器 | OpenClaw 在容器里，只挂载自己的工作区，经由网关访问宿主机 | 宿主机上的凭据和配置不在容器里；危险操作只能经过网关，拦截靠平台强制，不靠提示词 | 要多做一个网关服务；Orca 要配对 | **选用**（用户选定） |
| B. 宿主机专用系统用户 | 新建 `claw` 用户，用 npm 安装，以 systemd 运行 | 调用本机工具方便 | Orca 运行时属于登录用户，要额外授权；隔离强度取决于文件权限有没有配对 | 未选 |
| C. 宿主机以登录用户身份运行 | 靠 OpenClaw 自带的沙箱和执行审批 | 最省事 | 模型能直接动宿主机上的一切，危险拦截只能依赖 OpenClaw 的配置，配错一次就失守 | 排除 |

**验证结论（2026-11-20，用完即删的临时容器）**
- 容器内可以运行 Orca 命令行：把宿主机 `/opt/Orca` 只读挂进去，再装上 Electron 依赖库即可，版本 1.4.246。
- 用配对码执行 `environment add` 成功，`terminal list`、`worktree ps` 都能读到宿主机上的会话。
- Workbench 后端（8400）在验证时没有运行，未测到。它只监听 127.0.0.1，普通桥接网络的容器访问不到。

## 5. 总体架构

```
   智谱 API（GLM）        Telegram（用户私聊）
        ▲                    ▲     │                    ▲
        │ 模型请求            │ 回复│ 收消息            │ sendMessage（只发）
        │                    │     ▼ （唯一接收方）     │ 提醒、审批码
┌───────┴────────────────────┴────────┐   内部 token   ┌┴─────────────────────────────────┐
│ openclaw 容器（桥接网络）            │ ─────────────▶ │ assistant-gate 容器（host 网络）  │
│ - Telegram 渠道、会话、cron          │                │ 唯一通向宿主机的门                │
│ - SOUL / AGENTS 规则                 │ ◀───────────── │ - 白名单接口（会话/应用）         │
│ - skills（只调用网关）               │                │ - 危险操作拦截、审批码            │
│ - 挂载：仅自己的工作区               │                │ - 输出关卡：凭据脱敏              │
│ - 持有：Bot token、网关 token、      │                │ - 监视器（应用状态、会话等待）    │
│   智谱 API key                       │                │ - 审计日志                        │
└──────────────────────────────────────┘                │ - 持有：Orca 配对、Bot token(只发) │
                                                        └───────┬───────────┬──────────────┘
                                                                ▼           ▼
                                                          Orca 运行时   Workbench
                                                          (6768)        (127.0.0.1:8400)
```

**核心原则：一切触及宿主机的能力都必须经过 `assistant-gate`。**

原因：危险操作的拦截必须在平台层强制执行，不能只写在提示词里：SOUL 规则和平台层拦截两层并用。OpenClaw 容器里不放 Orca 配对信息、不能访问 Workbench、不挂载宿主机目录。即使模型被会话输出或日志里的恶意内容诱导，能做的事也只是网关白名单里的那些，危险的还要过审批。

### 5.1 openclaw 容器

- 固定 OpenClaw 版本（镜像带 tag），不使用 latest。
- 网关只监听容器内地址。控制台端口只映射到宿主机的 `127.0.0.1:18789`，需要时用 SSH 隧道访问。
- Telegram：只开私聊。`allowFrom` 只放用户本人的 Telegram ID，陌生人私信保持默认的配对机制。**不开群聊**：agent 框架可能把执行过程（命令、路径、报错堆栈、凭据片段）原样发到聊天里，提示词关不掉。
- 消息只发最终结果。如果 OpenClaw 支持关闭中间过程外发，就关掉（待实现时核实，见第 9 节）。
- 禁用技能市场自动安装，skills 只从本仓库来。
- 不使用参考教程里的 `dangerouslyDisableDeviceAuth`、`allowInsecureAuth`。
- 容器内的命令执行可以放开，因为容器本身就是沙箱，里面没有宿主机的凭据。外网不做限制，保留联网能力。
- 模型：OpenClaw 直连智谱 API（GLM），API key 只放在 OpenClaw 的密钥文件里。优先用 OpenClaw 自带的 Z.AI（GLM）provider；如果它不支持国内端点，就按"自定义 provider + Anthropic 兼容接口"配置。具体模型 ID 部署时从智谱当前的模型列表里选，要求支持工具调用。

### 5.2 assistant-gate（新写的服务，Python + FastAPI）

- 运行在 host 网络，只监听 OpenClaw 所在专用桥接网络的网关地址，用 Bearer token 鉴权。
- 镜像以 `debian:bookworm-slim` 为基础，装上 Electron 依赖库，宿主机 `/opt/Orca` 只读挂载。这样命令行版本始终与 Orca 服务一致。
- Orca 配对信息保存在网关自己的数据卷里，OpenClaw 容器看不到。
- 调 Orca 只通过固定参数的子命令，不拼接任意命令行。
- 调 Workbench 只用 `GET /api/status`、`GET /api/entries`、`GET /api/entries/{id}/logs`，以及经审批后的 `POST /api/entries/{id}/{start|stop|restart}`。
- Workbench 接受不带 Origin 头的写请求，任何能连上 8400 的程序都能写，所以绝不能让 OpenClaw 容器直接访问 8400。

**接口草案**（具体形式由实现者定）

| 接口 | 作用 | 分级 |
|---|---|---|
| `GET /sessions` | 会话列表（已脱敏） | 自动 |
| `GET /sessions/{id}/read` | 读取会话最近输出，有长度上限 | 自动 |
| `GET /search?q=` | 全文搜索会话 | 自动 |
| `GET /worktrees` | worktree 概况 | 自动 |
| `GET /sessions/pending` | 等待确认超过 5 分钟的纳管会话及其提示内容 | 自动 |
| `POST /sessions/{id}/reply` | 向会话发送回复 | 纳管会话自动，命中危险规则时转审批；非纳管会话只能在用户当次明确要求时回复 |
| `POST /sessions/{id}/manage`、`DELETE …/manage` | 标记或取消纳管（用户在 Telegram 里说"接管 X"/"放开 X"） | 自动 |
| `POST /agents/launch` | 在已有 worktree 启动 agent | 自动；任务内容命中危险规则时转审批 |
| `GET /apps`、`GET /apps/{id}/logs` | 应用状态和日志 | 自动 |
| `POST /apps/{id}/{start,stop,restart}` | 启停应用 | **始终需要审批**（D5） |
| `POST /approvals/{id}/confirm` | 提交用户的审批码 | 只能凭审批码 |
| `GET /audit` | 审计记录 | 自动 |

## 6. 权限与防护

### 6.1 三档权限

| 档 | 内容 | 执行方 |
|---|---|---|
| 自动 | 读状态、搜会话、读日志、普通的会话确认、启动 agent | 模型判断，网关执行 |
| 审批 | 危险操作；所有应用启停 | 网关拦下，用户凭审批码放行 |
| 禁止 | 少数不该由助手做的事（见 6.3） | 网关直接拒绝，审批也不放行 |

### 6.2 危险操作判定（由网关按确定性规则判断，不靠模型）

- 检查范围：发往会话的回复文本，加上会话正在请求确认的内容。比如 agent 问"是否允许执行 `rm -rf build/`"，即使模型只回复"y"，也算危险。
- 初始规则：
  - 删除类：`rm -r/-f`、`git clean`、删除 worktree 或分支。
  - 改写历史类：`git push --force/-f`、`git reset --hard`。
  - 数据库写和删：`drop`、`truncate`、`delete from`、`alter`。
  - 权限类：`chmod/chown -R`、`sudo`。
  - 远程脚本：`curl|sh` 类。
  - 服务和容器：`docker rm/prune`、`compose down`、`systemctl stop/disable`、`kill -9`。
  - 磁盘类：`dd`、`mkfs`。
  - 改动 `.env` 或凭据文件。
  - Orca 本身的高危子命令：`worktree rm`、`terminal close`、`environment *`、`account *`、`automations remove`。
- 模型拿不准的时候一律上报，不要自己批。这条写进 SOUL。

### 6.3 输出关卡、认证、漏洞防护

**输出关卡**
- 网关在返回结果前做凭据脱敏，覆盖密码、token、私钥、连接串、`.env` 键值等形式。原因：结果会发给智谱（外部模型服务）和 Telegram。
- 网关直接发出的提醒和审批消息也走同一套脱敏。
- 发给 Telegram 的只有最终结果，不发执行过程（见 5.1）。

**认证**
- Telegram 只认用户本人的 ID，其他人私信一律拒绝；不开群聊。
- OpenClaw 调网关要带 Bearer token；网关只监听专用桥接网络，宿主机上的其他容器和公网都连不到。
- 危险操作只能凭用户收到的一次性审批码放行（见 6.4）。

**漏洞防护**
- 不暴露端口：控制台只映射到宿主机 127.0.0.1，网关不对外。
- 固定 OpenClaw 版本，升级前先看更新说明，备份后再升。
- 禁用技能市场自动安装，skills 只从本仓库来。
- 会话输出和日志里可能夹带诱导性内容，模型照做时能动的也只有网关白名单，危险的要审批。

**禁止**（网关直接拒绝）
- Orca 的 `computer *`（桌面控制）、`skills share`、`artifacts share`（对外分享），以及 account、environment 管理类命令。

### 6.4 审批流程（模型无法自己批准）

1. 网关拦下操作，生成审批单和 6 位一次性码，有效期 10 分钟。
2. 网关直接用 Bot token 调 `sendMessage`，把操作说明和审批码发到用户私聊。Bot 收不到自己发出的消息，所以 OpenClaw 和模型看不到这个码。
3. 用户回复"批准 <码>"，OpenClaw 把码转交给网关的 `confirm` 接口。网关核对审批单 ID 和码，一致才执行；执行结果写入审计记录并通知用户。
4. 码用一次即作废。错误次数过多时作废该审批单。

### 6.5 凭据与数据

- 宿主机上的数据目录：`state/`（OpenClaw 工作区）、`gate/`（配对信息、审计记录）、`secrets/`（Bot token、网关 token、智谱 API key）。权限 700/600，不进 git。
- 脚本一律从环境变量或密钥文件读取凭据。SKILL.md 和规则文件里不写任何凭据，避免凭据散落各处难以收拾。

## 7. 主动提醒

监视器放在网关里，用确定性代码轮询，模型不参与采集：采集交给确定性脚本，模型只负责解读。

| 事件 | 检测 | 去向 |
|---|---|---|
| 应用挂了或恢复 | 每分钟读一次 Workbench `/api/status`；连续 2 次异常才算状态变化，变化才通知 | 网关直接发 Telegram，附带"回复'重启 X'由助手处理" |
| 会话等待确认（纳管会话） | 轮询 Orca，具体检测方式待核实（见第 9 节）；等待超过 5 分钟才算 | 写入 `/sessions/pending`，由 OpenClaw 的 cron（约每 3 分钟）交给模型判断并回复，危险的转审批 |
| 会话等待确认（非纳管会话） | 同上 | 只提醒用户，不代答 |
| 会话完成或空闲 | 同上 | 汇总通知 |
| 自动确认记录 | 网关审计 | 默认每小时汇总一次，不逐条推送（避免噪音） |

- 纳管名单存在网关自己的数据里：助手经 `/agents/launch` 启动的会话自动纳管；用户标记的按终端记录；会话结束后自动移出。
- 提醒去重：同一事件在恢复之前只发一次。
- 报告里写明数据采集时间，避免把过期缓存当成当前数据。

## 8. 部署与运维

- 仓库：本仓库。包含 compose 文件、网关代码、OpenClaw 配置模板（不含密钥）、SOUL/AGENTS 规则、skills。
- 部署方向只有一个：从仓库到容器。禁止在容器里直接改配置或 skill，避免两边各改各的。
- 升级前备份数据目录，旧镜像保留一周，回滚等于换回旧镜像加还原备份。
- Orca 配对：给网关单独生成一个配对设备，不与其他客户端共用，便于单独撤销。配对码只写入密钥文件，不经过聊天或日志。

## 9. 留给实现者核实或决定的事项

| 事项 | 说明 |
|---|---|
| OpenClaw 官方 Docker 镜像和版本 | 有官方镜像就用官方的并固定 tag，没有就基于 Node 24 自己构建 |
| 智谱接入方式和模型 ID | 核实 OpenClaw 的 Z.AI provider 能否用国内端点；不能就用 Anthropic 兼容接口自定义 provider。先用一个小任务测工具调用是否正常，再选定模型 ID |
| skill 怎么调用网关 | 优先用 MCP（如果 OpenClaw 支持远程 MCP），否则在 skill 里用脚本调 HTTP |
| 只发最终结果 | 核实 OpenClaw 的 Telegram 渠道能否关闭中间过程外发；不能的话，私聊里也要接受这个行为，并靠网关脱敏兜底 |
| 判断"会话正在等确认" | 可选来源：Orca agent 状态钩子（`agent hooks status`）、`terminal wait --for tui-idle`、屏幕预览特征。先测哪种可靠 |
| OpenClaw 能否由网关触发 | 如果 OpenClaw 有 webhook 或 hooks，等待确认的事件可以即时推给它，替代 cron 轮询 |
| Orca 本机地址 | 能否用本机地址生成配对，避免绕公网 IP |
| 访问宿主机端口 | 桥接网络默认能访问宿主机上监听 0.0.0.0 的端口（如 22、6768）。可选加 DOCKER-USER 规则，只放行网关端口 |

## 11. 实施中落定的决定与事实（2026-11-22 同步）

**用户已确认**
- 通知模式：网关已切到 `live`（`.env` 的 `GATE_NOTIFY_MODE=live`）。会话提醒的规则保持：只针对有 agent 状态的会话（Claude/Codex 等，不含普通 shell）；完成提醒 10 分钟窗口合并成一条；即时提醒每小时最多 12 条，超出的并入汇总；等待确认以 Orca 记录的 `stateStartedAt` 计满 5 分钟才算。
- Workbench 自身不可达：只记录在 `/monitor/status`，不推送（`GATE_NOTIFY_WORKBENCH_DOWN=0`），等 Workbench 恢复运行并稳定后再决定。

**实施细节（与第 5–7 节的差异或补充）**
- `assistant-net` 的网桥接口名固定为 `br-assistant`。容器访问宿主机自己的地址（含公网 IP 发夹）走 INPUT 链，不走 DOCKER-USER/FORWARD；规则放在自建链 `ASSISTANT-INPUT` 里。
- 会话"等待确认"的检测信号用 Orca agent 钩子状态（`worktree ps` 的 `agents[].state ∈ {blocked, waiting}` + `stateStartedAt`），该信号依赖 Orca 的 agent 钩子已开启。
- 用户"当次明确要求"的回复（设计 5.2 的 `reply` 行）网关无法验证，默认也要审批码（`GATE_USER_DIRECTED_REPLY=approval`），可选 `trust-flag`。
- 自动确认（不需审批）的条件 = 纳管 ∧ 当前正处于"等待确认 ≥ 5 分钟" ∧ 没命中危险规则 ∧ 该会话近 1 小时自动确认 < 20 次。危险判断的文本 = 回复 + 会话请求确认的内容 + 屏幕尾部 40 行。
- 审批：4 位 ID + 6 位码，码只存 HMAC；用户回复「批准 <ID> <码>」；每单错 5 次作废；一小时累计错 10 次锁定审批 1 小时并通知用户；未决单最多 5 张。
- 应用启停：接口与审批流已完成，开关 `GATE_APP_ACTIONS` 默认 `off`（关着时 403，不建审批单，不碰 Workbench）。
- `POST /agents/launch` 不在 P3 范围：Orca 启动 Claude 时附带 `--dangerously-skip-permissions`，助手若能拉起 agent，等于能拉起不受权限询问约束的 agent。建议要做的话每次启动都走审批。
- 已知局限：没有用真实的 Claude/Codex 权限询问验证"等待确认"信号（本机 Orca 终端里没有 `claude` 命令，且 Orca 启动 Claude 时跳过权限询问），用 Orca 的 agent 状态协议模拟验证。
